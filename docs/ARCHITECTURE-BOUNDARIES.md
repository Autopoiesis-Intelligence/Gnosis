# Gnosis Architecture Boundaries

## Canonical layers

- **Gnosis-Core:** trusted runtime and verification/commit path for trusted state transitions.
- **Gnosis-Memory:** intended role for machine-readable research, evidence, provenance and context-transfer material; verify the corresponding repository and deployed implementation before treating this role as operationally established.
- **Public Gnosis surfaces:** user-facing product, research and opportunity interfaces.
- **Separate production/factory layer:** any such layer must be identified from current repository, implementation and deployment evidence. A codename or architecture proposal alone does not establish its existence, deployment, or authority.

## Trust rule

Core is authoritative for trusted state. Downstream repositories and external services may receive or update material only through explicit controlled interfaces. They are never authority sources for Core merely because they are connected, private, or generated by an AI system.

## Context continuity

Authorized user/project context may move across sessions, devices and connected AI interfaces through explicit identity, permissions, project/context, version and provenance contracts. Continuity does not require exposing private runtime internals, and restoring context does not restore execution authority.

## Dependency rule

Core MUST NOT depend directly on research/context repositories, external AI models, connectors, UI, or commercial services. Any separate production layer may consume Core contracts only through explicit reviewed interfaces; it cannot bypass Core verification and commit.

## Historical labels

Older records may contain names such as `Genesis` and `Research-Memory`. They are retained as historical labels only and do not establish current repository names, deployment status, or authority boundaries.
